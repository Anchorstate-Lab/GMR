# AST 地图 —— 探针的通用观测机制

**这块电池不决定该检测什么。** 它提供一张地图和一套坐标；点位打在哪、
什么算变了，仍然是域的判断。

---

## 为什么需要它

现有的探针全是**扫全量**：把整个符号表吐出来，再比对两次的差集。这条路
有三个后果，全部在实测中撞上了：

```
名称漂移抓不到   扫全量只知道「集合变了」，要知道「同一个东西改了名」
                 得算两个数组的差集 —— 探针看不到历史，转换表没有集合运算
函数体内看不见   grep 式扫描只够到公开面，内联表达式的重复完全看不到
位置槽没被用     五个探针没有一个读 GMR_POSITION,而位置正是这套设计的核心
```

**换成「点位」就全部消失。** 盯一个点位时，「同一个位置上的东西名字变了」
就是位置上的事实变了，直接报——不需要差集。点位可以打在任何 AST 节点上，
包括表达式。而位置本来就是输入。

---

## 坐标

位置是**域定义的类型**（基底不解释它），但用这块电池的域需要一个约定的
坐标格式：

```
{
  file   ?  文件路径。缺省 = 全项目找
  kind   ?  归一化的节点种类：function · type · method · field · import …
  name   ?  标识符
  shape  ?  结构签名（参数类型 → 返回类型，或字段集）
  nth    ?  同名多个时取第几个。缺省 = 0
}
```

**四项都是可选的,合起来构成一个模糊坐标。** 这是有意的：一个精确坐标在
第一次改动后就会失效，而**代码本来就会动**。

## 匹配：不是找到或找不到，是「哪几项对上了」

```
输出 {
  found       有没有匹配到
  matched     对上了哪几项  ["file","kind","name"]
  missed      对不上哪几项  ["shape"]
  at          实际找到的完整坐标 —— 域可以拿它去 Restate
  node        那个节点的事实（名字·签名·体的哈希·行号）
  candidates  并列最优的有几个 —— 见下
  extractor   提取器自己的内容哈希
}
```

**腐坏的类型直接由 `missed` 读出来,不需要额外的探针:**

```
missed = ["name"]              名称漂移 —— 位置对，东西还在，名字变了
missed = ["file"]              搬家 —— 该 Restate 把位置挪过去
missed = ["shape"]             契约漂移 —— 签名变了
missed = ["shape"] 且 body 变   实现也变了
found = false                  一项都没对上
```

### `candidates`：写实现的时候才发现少了它

**光凭 `missed` 分不开「改名了」和「真没了」——两者都是 `missed=["name"]`。**
实测：坐标 `{file,kind,name}` 里名字对不上时，`file+kind` 得 2 分的候选
在那个文件里有一大把，探针只能在并列里随便挑一个报回来，`at` 完全不可信。

分开它们的是**并列了几个**：

```
candidates = 1     唯一解。东西确实还在，可以放心拿 at 去 Restate
candidates = 一堆   我在并列里挑了一个。at 是猜的，别据它挪位置
```

而让 `candidates` 收敛到 1 的，是坐标里带上 `shape`：签名把「同一个东西」
钉死了，改了名也还是它。**所以要用来抓名称漂移的点位，坐标必须写 `shape`。**
只写 `{file,kind,name}` 的点位抓得到「有东西不对」，抓不到「是哪个」。

`found=false` 只在**一项都没对上**时出现，比 DESIGN 原来设想的窄 ——
「真没了」的实际读法是 `candidates` 很大而不是 `found=false`。

一个机制,一次观测,覆盖名称漂移 · 搬家 · 契约漂移。**域只需要在转换表里
写它关心哪一项。**

## 匹配策略

按 `file → kind → name → shape` 的顺序逐项收窄。**任何一项匹配失败都不
终止**，而是记进 `missed` 继续用剩下的项找。最后按匹配项数取最优候选；
并列时按 `nth` 取。

这意味着**探针永远尽力给出一个答案**，而不是简单地报「找不到」。找不到
和找到了但对不上，对 Agent 是完全不同的两件事。

## 语言无关

用 tree-sitter，不用 `syn`。

```
syn           只有 Rust。现在的提取器就是它 —— 换个项目直接报废
tree-sitter   几十种语言,一套 API,统一的树
```

各语言的节点种类名字不同（Rust 是 `function_item`，Python 是
`function_definition`，TypeScript 是 `function_declaration`）。**归一化那
一层是这块电池的主要工作**：

```
function  函数 / 方法 / 闭包声明
type      结构体 / 类 / 接口 / 枚举 / 类型别名
field     字段 / 属性
import    引入 / 依赖声明
call      调用点
```

归一化表按语言分别声明，**加一门语言 = 加一张表,不改机制**。

**现状：只有 Rust 一张表。** 机制是语言无关的（表是数据，按扩展名挑），
但「加一张表就行」这句话在第二张表真的出现之前是**未经检验的声称** ——
读到这里的人不要把它当已完成的事。

---

## 它不做什么

- **不决定点位打在哪。** 那是域的判断
- **不判断「变了对不对」。** 它只吐事实，判断在转换表里
- **不 ship 任何预设的点位集合。** ship 一份「该检测什么」的清单是红牌，
  主语是基底和产品都不行

---

## 与现有五个探针的关系

仓库根 `probes/` 那五个（符号表 · 依赖图 · 方言 · 判据本体 · 规模）
**是为这个仓库写的,也应该是**。换一个项目时探针由那个项目的 Agent 自己
写——拿我们的探针去测别人的项目做不到，那样反而成了「ship 检测清单」。

它们的价值是**示范**：说明一个探针该长什么样、派生指标与全量证据怎么分层、
失败契约怎么守。这块电池的价值是**机制**：让那些探针不必各自实现 AST 解析。

两者不冲突：电池提供地图，域决定在地图上盯哪儿。
